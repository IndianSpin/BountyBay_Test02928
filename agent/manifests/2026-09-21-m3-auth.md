# Context Manifest — M3 auth + profiles

## Objective

Milestone 3 of 16_IMPLEMENTATION_SEQUENCE.md: Clerk authentication isolated
behind an internal adapter (DEC-023), the internal User/PlayerProfile model
wired to PostgreSQL, anonymous-handle creation and selection (PRD-001), and
protected/public API routes (08_API_CONTRACTS: GET /v1/me, GET
/v1/profiles/:handle) plus a dev-mode adapter so local/CI work runs without
Clerk keys.

## Relevant rule / requirement IDs

DEC-023; PRD-001, PRD-002; 06_ARCHITECTURE.md §2 (auth, AuthIdentity adapter);
07_DATA_MODEL (User, PlayerProfile); 08_API_CONTRACTS.md; SI-005 (rate
limiting); SI secrets policy (names only in .env.example).

## Files expected to change

- packages/db/src/user-repository.ts (+ exports) — internal user keyed by
  auth subject, default unique anonymous handles, handle validation/updates,
  private /v1/me and public profile DTOs
- apps/api: src/auth/adapters.ts (AuthAdapter interface, Clerk networkless
  JWT verification, HMAC-signed DevAuthAdapter, factory that refuses
  production without config), src/app.ts (buildApp factory + routes + rate
  limiting + auth preHandler), src/server.ts (env loading), tests/*
- apps/web: guarded ClerkProvider/middleware (keyless dev passes through),
  /sign-in, /profile (client fetch of /v1/me with the Clerk token),
  auth-status on home
- Root: vitest include for apps/*/tests, test:db sequential mode, .env.example

## Explicitly out of scope

M4 realtime, rating updates (M6), profile privacy controls (OQ-011),
monetization, email verification beyond Clerk defaults.

## Tests required

Adapter: dev token round-trip, garbage/tampered/wrong-secret rejection,
factory selection incl. production refusal. Routes (DB): 401s, dev sign-in →
me → handle → public profile end-to-end, idempotent sign-in, case-insensitive
handle uniqueness, validation errors. All gated on RUN_DB_TESTS.

## Result

- Changed files: as listed above.
- Behavior implemented: token → subject → internal user mapping; default
  handle allocation (adjective+noun, "BlackParrot" in the pool); handle
  choice/change with case-insensitive uniqueness; exact 08 public profile
  shape; rate limits per SI-005; dev sign-in refused in production.
- Tests added/run: 9 adapter unit tests + 7 route tests (26 DB-gated total
  across packages/db and apps/api). Full chain green: lint, typecheck
  (7 packages), 142 unit tests, 26 DB tests, production build. Live smoke
  test passed: sign-in → /v1/me → public profile → 401s.
- Unresolved issues: Clerk keys not yet provisioned (dev adapter covers
  local; production factory refuses to boot without CLERK_JWT_PUBLIC_KEY).
- Spec ambiguities encountered:
  1. Handle change frequency is unspecified (PRD-001 covers defaults only) —
     implemented freely changeable; flag for a product decision if it matters.
  2. Case-insensitive uniqueness is enforced in the application layer; the DB
     unique index is case-sensitive (noted in code).
  3. Default handle format (adjective+noun) is an implementation choice
     consistent with the docs example "BlackParrot".
- No-spec-change confirmation: no canonical document modified. No
  decision-log updates (no product decisions made; handle-change policy
  flagged above as open to review).
